### 1. 주요 학습 내용
#### a. **객체지향 설계 원칙** 적용 (MVC)
이번 미션에서는 이전 과제의 피드백을 반영하여 **MVC 패턴**을 직접 적용해 보는 것이 주요 학습 목표였다.  
특히 **객체 지향 설계 원칙(SRP, OCP, DIP 등)** 을 염두에 두고 각 클래스의 책임을 명확히 분리하였다.
- `CarRaceController`: 게임의 전체 흐름 제어 (입력 → 시뮬레이션 → 출력)
- `CarRaceService`: 핵심 로직 담당 (자동차 이동, 우승자 계산)
- `RacingCar`: 데이터 모델 (이름, 위치, 이동 메서드)
- `InputView` / `OutputView`: 사용자 입출력 담당

이를 통해 각 클래스가 **단일 책임 원칙(SRP)** 을 따르도록 설계하였으며,  
테스트와 유지보수가 훨씬 용이해짐을 체감할 수 있었다.

#### b. **Stream API** 
`Stream API`는 Java의 컬렉션을 함수형 방식으로 다루는 도구로,  
이번 미션에서는 **반복문을 간결하게 표현하고 View의 책임을 명확히 분리하기 위해** 사용했다.

기존 방식에서는 매번 `for`문을 돌며 `System.out.println()`을 반복적으로 호출했지만,  
`Stream API`를 사용하면 **데이터를 변환(map)** 하고 **결과를 수집(collect)** 하는 흐름을  
간결하고 선언적으로 표현할 수 있었다.

예시 코드를 보며 이해해 보자
```java
// 예시: RacingCar 객체 리스트에서 우승자 이름만 추출
List<String> winnerNames = cars.stream()                // 1. 스트림 생성
        .filter(car -> car.getPosition() == maxPosition) // 2. 조건 필터링
        .map(RacingCar::getName)                        // 3. 이름 추출 (매핑)
        .collect(Collectors.toList());                  // 4. 결과를 리스트로 수집
```
.stream : stream객체를 생성함(기술적으로는 객체가 맞는데 데이터흐름을 처리하는 도구 정도로 생각하면 됨 -> [stream의 특징](\#-스트림의-특징))
.map : mapping의 map(자료구조 Map아님!) racingCar객체 stream에서 getName메소드를 통해 name만을 추출 주로 람다식 형태로 사용되며 .map(현재 요소 타입, 변환함수가 반환할 새로운 타입)
.collect : 위의 stream을 다시 list로 collect하는 메소드 인자로 Collectors 객체의 .toList()를 호출하여 list로 만듬

이렇게 하면 다음과 같은 장점이 있었다.
- 코드의 가독성 향상: "무엇을 하는지"가 명확하게 드러난다.
- View의 역할 분리: 출력 로직을 간결화하여, 출력 책임이 Controller나 Service에 섞이지 않게 됨.
- I/O 최소화: StringBuilder나 Collectors.joining() 등을 활용하여
콘솔 출력 호출을 최소화하고 한 번에 처리하도록 개선.

\# 스트림의 특징<br>
사용목적은 데이터를 필터링, 변환 하기 위한것임!
1. 데이터 저장소가 아님: 스트림 자체는 데이터를 저장하거나 보관하지 않습니다. 그저 원본 컬렉션에서 데이터를 가져와 파이프라인을 통해 처리하는 '흐름' 역할

2. 일회용: 스트림은 한 번 사용되면 닫히므로, 동일한 스트림을 두 번 이상 재사용할 수 없다. (데이터를 다시 처리하려면 원본 컬렉션에서 새 스트림을 다시 생성해야 함)

3. 함수적: 스트림은 함수형 프로그래밍 개념을 자바에 도입하여, 데이터를 '어떻게 처리할지'가 아니라 '무엇을 할지'를 선언적으로 명시함

4. Stream을 생성할 수 있는 주요 대상
   - Collection
   - 배열 (Array)
   - Map
   - Etc(Files, Randoms 등)
```java
// 간단한 Stream 동작 예시
List<String> carNames = Arrays.asList("pobi", "woni", "jun");

carNames.stream()                   // 스트림 생성
        .map(String::toUpperCase)   // 변환: 대문자로 변환
        .filter(name -> name.length() <= 5) // 필터링: 이름 길이 5 이하만
        .forEach(System.out::println);      // 결과 출력
```


### 2. 미션 후기
이번 미션을 통해 단순히 기능 구현뿐 아니라 코드 구조와 역할 분리의 중요성을 체감했다.
기존에는 “작동하는 코드”를 만드는 데 집중했지만,
이번에는 “읽기 쉬운 코드”와 “확장 가능한 코드”를 고민했다.

특히 MVC 패턴을 직접 적용하면서 Controller가 Service와 View를 명확히 구분하고,
각 클래스가 한 가지 역할만 담당하도록 설계하는 것이 얼마나 중요한지를 깨달았다.

또한 Stream API를 활용해 코드를 간결하게 유지하면서도
불필요한 반복문을 제거해 깔끔한 코드를 작성하는 경험을 얻었다.
이 과정에서 함수형 사고방식의 유용함을 실감했고,
다음 미션에서는 테스트 코드와 예외 처리를 더욱 철저히 다뤄볼 계획이다.

#### 🚫 8. 축약하지 않는다
- **적용 여부:** ⚠️ 부분 준수
- **설명:**  
  전반적으로 변수명과 메서드명을 축약하지 않고 의미가 명확하게 드러나도록 작성했다.  
  예를 들어, 경주 횟수를 의미하는 변수는 `trialCount`로 명명하여 의도를 명확히 표현했다.  
  다만 일부 코드에서는 반복 카운트를 표현하기 위해 `cnt` 등의 축약형을 사용한 부분이 있다.  
  이후 미션에서는 `count`, `index`, `length` 등 완전한 단어로 표현하여  
  **축약 없이도 명확히 읽히는 코드**를 작성하도록 개선할 계획이다.

### 💡 종합 평가
1주차 Discord 피드백의 핵심은 “요구사항 충실 + 코드 기본기 + 명확한 구조”였다.  
이번 `java-racingcar-precourse` 프로젝트에서는 다음 점에서 이를 잘 준수했다.

- MVC 패턴을 적용하여 **책임 분리 원칙** 준수
- Stream API로 **가독성과 선언적 코드 스타일** 확보
- 커밋 메시지를 통해 **작은 단위의 변화 기록** 실천
- 의미 있는 이름과 코드 포맷으로 **읽기 좋은 코드 구현**

앞으로의 목표는 `.gitignore`와 **디버깅 습관 고도화**,  
그리고 테스트 코드(`JUnit5 + AssertJ`)를 활용한 **자동화된 검증 프로세스 확립**이다.
